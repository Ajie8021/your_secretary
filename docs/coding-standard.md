#  代码规范

## 1. 基本原则

- 使用微信原生小程序与 Vant Weapp；后端使用微信云函数。
- 代码优先保持简单、可读、职责单一，不为 MVP 引入不必要的框架或抽象。
- 页面负责展示和交互，云函数负责业务规则、数据校验和权限控制。

## 2. 命名规范

- 页面与目录：小写英文，如 `task`、`profile`、`feedback`。
- 云函数目录：使用约定名称，如 `login`、`task`、`note`、`user`、`admin`、`feedback`、`sendReminder`。
- JavaScript 变量和函数：`camelCase`，如 `loadTasks`、`remindAt`。
- 常量：语义明确；固定配置集中定义，避免散落的魔法值。
- 数据库字段：统一使用现有 `camelCase` 字段名，不随意改名。

## 3. 格式与结构

- 使用 UTF-8 编码，统一缩进（2 个空格）。
- 一个函数只处理一个清晰职责；较长流程拆分为可复用的小函数。
- 页面逻辑、云函数业务逻辑、数据访问逻辑尽量分离。
- 避免重复代码；公共校验、响应格式和错误处理可抽取为小型公共模块。
- 删除无用代码、调试输出和未使用变量；提交前检查控制台错误。

## 4. 前端规范

- 页面数据通过 `data` 管理；更新页面状态使用 `setData`。
- 异步调用云函数、上传图片时处理成功与失败分支，避免只写成功路径。
- 表单提交前做基础校验；关键校验必须在云函数重复执行。
- 加载中、空列表、失败、成功等状态应有明确反馈，避免误报保存成功。
- 不在前端硬编码管理员权限判断作为安全措施；前端仅可用于控制入口显示。

## 5. 云函数与安全规范

- 每个云函数入口明确解析 `action` 和参数，并校验必需字段、类型、长度与允许值。
- 用户身份使用云函数上下文取得的 `OPENID`；不信任客户端传入的 `_openid`。
- 用户数据读写必须限定当前 openid；管理员操作每次都在云函数侧检查 `admins` 白名单。
- 更新数据使用字段白名单，禁止客户端修改 `_openid`、`createTime`、`reminded` 等服务端控制字段。
- 错误响应简洁一致；详细异常写入服务端日志，不向前端泄露堆栈或敏感信息。
- 数据库操作失败时返回失败状态，前端不得提示操作成功。

## 6. 数据与业务规则

- 任务 `level` 仅允许整数 `1`–`4`；DDL、内容必填。
- 任务排序统一为：`top` 降序、`level` 降序、`ddl` 升序、`createTime` 降序。
- 随笔排序统一为：`top` 降序、`createTime` 降序。
- 默认任务名为 `无名`，默认随笔标题为 `无题`；置顶默认 `false`。
- 提醒时间修改后重置发送状态；关闭提醒时清除提醒时间。仅在订阅消息发送接口确认成功后标记已发送。
- 用户只能修改自己的未回复反馈；管理员回复前必须通过白名单鉴权。

## 7. 异常处理与日志

- 对云函数调用、数据库读写、图片上传和订阅消息发送分别处理异常。
- 给用户展示可理解的提示；不要只吞掉异常或只打印日志。
- 日志应包含定位问题所需的操作、记录标识和错误码，不记录不必要的个人信息。
- 定时任务中单条记录失败不得导致整批任务直接中断。

## 8. 注释与提交

- 注释解释业务原因、边界条件或不直观逻辑，不逐行翻译代码。
- 复杂排序、权限判断、提醒状态变化等关键规则应有必要说明。
- Git 提交应小步、可理解，提交信息描述实际变更，例如：
  - `feat: add task CRUD`
  - `fix: validate reminder time`
  - `test: cover feedback permission`
  - `docs: update design specification`
- 一个提交尽量对应一个明确目的；不要将无关修改混在同一提交中。

## 9. 最低测试要求

每个模块至少覆盖正常流程、输入错误和权限边界。重点验证：
- 用户数据隔离与管理员白名单；
- 任务四象限映射、排序、置顶和提醒状态；
- 订阅授权拒绝、发送失败与定时任务异常；
- 反馈回复后禁止修改；
- 图片上传失败时页面状态正确。
